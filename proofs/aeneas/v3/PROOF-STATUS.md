# Formal verification ledger — production v3 core

**Reconciled 2026-11-03** (whether a keyless audit needed the key, `commit_needs_no_key`, and what a keyless audit that needed none establishes, `Audit`, `History`; the hook's per-entry check in the core, `Staged`; the selection-independent A24 history, `ProductSecurity`; the stored key and its primitives, `KeyUse`; the audit's per-entry check, `audit_check`, and the keyed audit of one commit, `Audit`; the hook's and the audit's loops in the core, `index_verdict` and `commit_verdict`; the top-level statement `transcrypt_product_assurance`, `ProductAssurance`; merges, branches and rekeys, `transcrypt_product_assurance_dag`, `History`). Every theorem below is about the Charon/Aeneas
translation of the production `rust/crates/transcrypt-v3-core/src/lib.rs`
(pinned by `SNAPSHOT.json`), stated against the independent specification in
`proofs/lean/Transcrypt/{V3Wire,V3WireCodec,V3Policy}.lean` and `V3Policy/*.lean`. All but the
program equality `record_envelope_prefix_ok_record` are `WP.spec` triples,
so they also exclude panics (index, overflow) and divergence. The
default `V3Wire` target builds all of them;
`bash proofs/aeneas/check-v3-axioms.sh` confirms that all 191 theorems listed in
`audit/Axioms.lean` (those named in the table below) use only `propext`,
`Classical.choice` and `Quot.sound`. No `sorry`, `admit`,
`axiom`, `native_decide` or `bv_decide` occurs in any verification module
(enforced by `v3_snapshot.py verify`).

**Correction (2026-10-25).** Until this date the audit script read only the
first line of each `#print axioms` report, and Lean wraps long lists. The two
frame-decoding theorems then depended on `bv_decide`'s native-evaluation
axioms, which the audit did not report. The lemma `be32_bv` is now proved bit
by bit without `bv_decide`, and the script parses complete reports (checked
against a wrapped list containing a native axiom).

Shared lemmas, loop rules and tactics are in `V3Wire/Verification/Basic.lean`
(`unfold_v3_bytes`, which unfolds the spec's named bytes, in `Tactics.lean`);
the snapshot proofs are split into `Snapshot{Listing,Order,Attrs,Lookup,Moves,Policy}`
(aggregated by `Snapshot.lean`).

For the cross-component picture see
[`V3-PROOF-COVERAGE.md`](../../../docs/verification/V3-PROOF-COVERAGE.md) and
the trust-ordered [`V3-ASSUMPTIONS.md`](../../../docs/verification/V3-ASSUMPTIONS.md).

## Explicit assumptions in the statements

- **`Realizes inst prims σ`** (Protocol, Lifecycle): the `V3Primitives`
  instance computes the abstract suite's deterministic SIV with the spec's
  domain strings and AD order, preserves `&mut` slice lengths, never claims
  success wrongly, opens genuine right-sized records, and computes the
  truncated digest. Production instance `transcrypt_rs::Keyed` is checked
  by `rust/crates/transcrypt-rs/tests/v3_differential.rs` against a corpus
  from OpenSSL AES-SIV (`tests/v3/reference/differential.py`), and its
  clauses by `keyed_satisfies_the_realizes_contract` (A5).
- **`Suite`** fields: SIV output length, injectivity per AD (true of any
  deterministic AE), digest length. Unforgeability/confidentiality are
  computational assumptions (A10), not Lean theorems.
- **Lifecycle models** follow the adapter's call order (A4, reviewed in
  `V3-ASSUMPTIONS.md`).
- **Snapshot preconditions.** The snapshot queries are stated for a
  listing `parse_listing` accepted (`ListingOf`, and `Sorted` or
  `PathOrdered`); that is the only way the adapter obtains `ends`. The
  object-id lookups take an order `object_order_ok` accepted; the adapter
  sorts it and the core checks it.
- **History contracts** (`ProductSecurity`): `GuardedHistoryStep` (the next `HEAD` is made from the checked index and has its policy entries, A22; objects keep their content, A11, `CommitStep`) and the start of the history: the first commit's `HEAD` records authenticate if its check trusted `HEAD` (A24; established by a full keyed check, or by the keyed audit of the commit `HEAD` names, `audited_head_starts_keyed_history`, itself given its parent's records when it trusted the parent). No selection contract: the invariant `RecordsAuthentic` does not mention selection, so local attribute sources need not be fixed.
- **Audit contracts** (`Audit`): `AuditContracts` (every non-reserved entry of the commit not examined is the first parent's exactly, and only while the configuration is unchanged; the facts passed to `audit_check` and the blobs read are Git's, A20, A19, A11, A21), `AuditAnswers` (A4), `AuditSelectionAgrees` (A19: an unexamined entry is selected as in the parent; the adapter examines the whole tree when an attribute file changes), and the parent's records when the audit trusted it (a parent audited before it, or outside the audited range, A13).
- **End-to-end contracts** (`EndToEnd`): `GitListing` (A20),
  `GitAttributes` (A19), `GitObject` (A11, A21), `Realizes` (A5), the
  observed call results `HookEvidence`, the one call of the extracted loop `index_verdict` (`HookAccepted`), and the meaning of the adapter's blob reads and three answers to the verified verdict in the states the run reaches, `HookAnswers` (and `RepairInputs`/`RepairContracts` for the repairs, whose only model is what each reported `RecordClass` means, `RecordEvidence`) (A4); no handwritten loop remains on the hook's check,
  the sequencing state (A23); Git commits the checked index (A22).

## Not covered by Lean

AES-SIV/Argon2id/SHA-256 implementations and security, the Unix credential
agent's IPC and process isolation, Git's attribute/index semantics, and
filesystem atomicity. See the assumption register for evidence and residual
risk of each.
