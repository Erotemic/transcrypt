# Production v3 Rust extraction through Charon/Aeneas

The formal-verification target is the actual `transcrypt-v3-core` crate used
by the Rust executable. Its four fixed-width codec functions implement the
byte-level decisions modeled independently in `proofs/lean/Transcrypt/V3WireCodec.lean`.
The first obligation is to *extract* those four functions and compile their
Aeneas-generated Lean definitions. A later obligation is to prove that those
definitions refine the independent specification. Compilation alone does **not**
discharge the latter obligation.

## Tooling (Ubuntu/Linux)

Use the supported [hax 0.4 Lean backend](https://pereq.dev/hax/manual/lean/quick_start/)
instead of cloning or separately building Charon and Aeneas. `cargo-hax`
selects a matching Charon/Aeneas pair, downloads their prebuilt binaries,
checks their release-manifest hashes, and manages a compatible Lean package.
This has **no effect on the Bash or Rust runtime dependencies**; it is only
needed by developers verifying the Rust implementation.

With `rustup`, Cargo, and Lean (`elan`) installed:

```bash
cargo install --locked --version 0.4.2 cargo-hax
cd ~/code/transcrypt
bash proofs/aeneas/translate-v3-core.sh
bash proofs/aeneas/build-v3-generated.sh
```

The first command may download and compile `cargo-hax`. Its 0.4.2 version
output uses separate `version=0.4.2` and `commit=...` lines; the driver
script checks the exact version field rather than assuming a single line. The translation script
then validates the scenario with `cargo hax extract --dry-run v3-wire`,
installs matching tools via `cargo hax tools install`, and runs
`cargo hax extract v3-wire` from the actual crate directory. No `AENEAS_ROOT` environment variable or separate
`~/code/aeneas` repository is needed. Avoid independently pinning Aeneas and
Charon to arbitrary commits: use the pairing tested with cargo-hax 0.4.2.

The declarative selection lives at
`rust/crates/transcrypt-v3-core/hax.toml`. Hax generates the Lean project at
`rust/proofs/aeneas/generated/V3Core/lean/`, inside the Rust workspace
(as required by hax 0.4.2), and excluded from Git. The accompanying
`PROVENANCE.txt` records the Rust source hash, scenario hash, managed tool
versions, and generated sources. The ordinary `proofs/lean` project remains
independent of Aeneas, with its own toolchain.

## Strict proof boundary

`build-v3-generated.sh` refuses missing/empty extraction modules and admitted
(`sorry`, `admit`, `axiom`) generated or external-model Lean declarations. It
requires the generated root to import `V3Wire.Extraction`, then runs Lake on
that module. If the toolchain produces external model templates containing
holes, the build stops: those models need explicit, reviewed contracts.

The independent Lean proofs (`V3WireCodec`) and generated Lean functions must
still be connected by real refinement theorems. Cryptographic library
correctness, Argon2id and AES-SIV security, runtime filesystem effects, and
Git index transitions are **separate** obligations. Do not treat translation
or a successful Lake build as a formally verified end-to-end product.

## Integrated generated-code/specification proof workspace

After extraction, `build-v3-generated.sh` automatically runs
`prepare-v3-refinement.sh`, which copies **verbatim** the independent
`Transcrypt/V3Wire.lean` and `Transcrypt/V3WireCodec.lean` into the generated
Lake package under the separate `Transcrypt` module root. The generated
`V3Wire` root then imports `V3Wire.Verification.IndependentSpec`, a module
importing **both** `V3Wire.Extraction` (from actual Rust) and
`Transcrypt.V3WireCodec` (independent specification). This copy is only in the
Git-ignored generated directory; it never alters the reviewed specification.

The integrity gate `check_v3_proof_tree.py` requires the extraction to match
current Rust source/hax scenario hashes **and every hax-owned generated Lean
source hash**, the specification copies to match byte-for-byte, and the
*reachable* local Lean import graph to be free of
`sorry`, `admit`, and `axiom` declarations (ignoring those words in strings and
comments). Unimported Aeneas external-model templates are evidence for later
work, not trusted proofs. The build uses the exact Lean version generated by
hax for both libraries. These checks establish provenance and compatibility;
they are **not** the Rust-to-spec refinement theorem.

Run:

```bash
cd ~/code/transcrypt
bash proofs/aeneas/translate-v3-core.sh
bash proofs/aeneas/build-v3-generated.sh
python3 proofs/aeneas/tests/test_v3_proof_inputs.py -v
```

### Export the actual generated Lean definitions for refinement

For work on the *first real refinement theorem*, provide the generated Lean
functions and their types rather than guessing their names or signatures.
Produce an allowlisted, deterministic source bundle (no Git worktree content,
passwords, credential-agent sockets, `.lake` build directories, or other
runtime state):

```bash
cd ~/code/transcrypt
python3 proofs/aeneas/export_v3_proof_inputs.py \
  --output ~/Downloads/transcrypt-v3-generated-proof-inputs.zip
```

This ZIP contains actual Aeneas-generated Lean source (including unimported
external-model templates, clearly distinguished from imported code), the
independent spec, production Rust source, the extraction scenario, provenance,
and a SHA-256 manifest. **It is source for proof development, not proof
completion.** Its creation rejects stale Rust extraction and modified
independent spec copies. Sharing this bundle allows a proof author to create
`V3Wire/Verification/Refinement.lean` theorems against the actual generated
functions, then build those theorems in the same Lake project. That is the
unmet next acceptance condition.

The no-toolchain regression tests are narrow and must not be confused with
Aeneas or Lean execution:

```bash
python3 proofs/aeneas/tests/test_v3_proof_inputs.py -v
```

## Tracked production v3 proof snapshot (current recommended gate)

The real generated Lean codec definitions are now tracked under
`proofs/aeneas/v3/`, with exactly pinned Charon/Aeneas, Lake dependencies, and
SHA-256 bindings to the Rust source and hax extraction scenario. Do **not**
commit anything under `rust/proofs/aeneas/generated/` or `.lake/`.

Ordinary changes no longer need to reinstall or rerun Charon:

```bash
cd ~/code/transcrypt
python3 proofs/aeneas/v3_snapshot.py verify
bash proofs/aeneas/build-v3-tracked.sh
```

The build stages the one authoritative spec from `proofs/lean/`, imports the
actual extracted Rust codec definitions, and compiles the **first direct
source-derived refinement claims** (version-marker correspondence/disjointness).
Complete encoder/decoder, authentication and Git lifecycle refinement is still
open. See `proofs/aeneas/v3/PROOF-STATUS.md` for the precise proof boundary.

On verified Rust changes, run `translate-v3-core.sh`, then
`python3 proofs/aeneas/v3_snapshot.py compare`; update the snapshot only
with the explicit reviewed `refresh` command. CI both builds the checked-in
proof package and independently regenerates/compares the extracted Lean.

This separate, opt-in Lean 4.31 target checks proofs directly about the
